## 0. 一句话结论

定位胆玩法的核心盈亏计算被放大了 5 倍：`_profitFor()` 把「整组总投入 5A」当成「单注金额 A」再乘以 `(5.8 − 5)`，导致每笔命中被记为 `+4A`，正确值应为 `+0.8A`。生产库已确认该错误正在实跑：命中 5 注各 10（总投入 50）被记 `+40`，正确为 `+8`。

## 1. 缺陷清单（按严重度）

### P0-1　赢单净利被放大 5 倍（金额缩放错误）

**位置**：`src/services/strategy-executor.service.js` → `_profitFor()`（约 629–642 行）

```js
_profitFor(chatId, direction, betAmount, isWin) {
  const parts = splitDirectionParts(direction);
  const a = Number(betAmount);
  if (parts.spec && !parts.big) {
    return isWin
      ? Math.round(a * (locationPayoutOdds() - NUMBERS_PER_BET) * 100) / 100
      : -a;
  }
  return isWin ? this._winProfit(chatId, a) : -a;
}
```

**事实链**：

1. `handleRoundOpen()`（约 284–302 行）计算 `totalStake = amount * NUMBERS_PER_BET`（5A），写入 `action_logs.bet_amount`。
2. `_profitFor()` 收到的 `betAmount` 就是这个 **总投入 5A**。
3. 分支里 `a * (5.8 - 5)` = `5A × 0.8` = **4A**。
4. 正确口径（项目自身在 `rule.engine.js` 里写明的定义：命中一注返还 `5.8A`，整组投入 `5A`）应为 `5A × 5.8 − 5A = 0.8A`。
5. 正确公式应为 `(a / NUMBERS_PER_BET) * (locationPayoutOdds() - NUMBERS_PER_BET)`。

**生产数据佐证**（生产库 `action_logs`）：

| id | 每注金额 | 总投入 bet_amount | 记录 profit | 正确 profit |
|----|---------|------------------|------------|------------|
| 20680 | 10 | 50 | **+40** | +8 |
| 20670 | 100 | 500 | **+400** | +80 |

生产规则 `base_bet=10, martingale_ratio=10`，逐级金额 10 / 100 / 1000（总投入 50 / 500 / 5000），正确净利应为 +8 / +80 / +800，当前代码记录为 +40 / +400 / +4000，倍投后误差同步放大。

**影响面**（同一个 `_profitFor()` 被 6 条结算路径共用，全部继承该错误）：

- 骰子直判 `_settlePendingWithDice()`
- 结算消息兜底 `handleSettleMessage()`
- 发送确认补结算 `handleBetConfirmed()`
- 开盘兜底 `_sweepPendingAtRoundOpen()`
- 模拟钱包结算 `_applySettlement()` → `creditSimBalance(bet_amount + profit)`
- 止盈判定 `checkTakeProfit()` → `getTodayProfit()` → `sumProfit()`
- 报表展示 `report.panel.js` / `dashboard.panel.js` 的「今日盈利」

**量化影响**：生产保留窗口内已结算 54 条（41 赢 / 12 输 / 1 待结算），程序记录盈利合计 `350150`；按正确模型重算为 `24550`，**差额 325600**，仅此窗口就多计了 32.5 万。模拟钱包当前 `1056420`（初始 700000），因一小时清理策略更早记录已不可见，无法完整反推，但资金曲线被显著抬高已确认。

**修复**：

```js
if (parts.spec && !parts.big) {
  const perNote = a / NUMBERS_PER_BET;          // 单注金额
  return isWin
    ? Math.round(perNote * (locationPayoutOdds() - NUMBERS_PER_BET) * 100) / 100
    : -a;
}
```

### P1-1　`bet_amount` 单位无版本标记，旧库与新库会静默混算

`migrations/010_spec_mode.sql` 只新增了 `rules.mode`，没有给 `action_logs.bet_amount` 增加金额口径字段。2026-10-31 口径从「单注 A」改为「总投入 5A」时，历史行没被迁移、也没被标记。

- 旧行的 `bet_amount = A`，`_profitFor()` 会算出 `A × 0.8 = +0.8A`（碰巧等于正确净利），但输单时是 `-A` 而非 `-5A`，资金曲线自身矛盾。
- 新行的 `bet_amount = 5A`，算成 `+4A`（错误）。
- 两种行在同一个库里无法区分，代码也没有任何判别逻辑。

**修复建议**：加 `action_logs.amount_scope`（`PER_NOTE` / `TOTAL`）或独立字段 `stake_per_number`，读取时按列取值，不再靠 `bet_amount` 猜。

### P1-2　结算名单「赢/输」字段语义未验证，且多规则同群会重复套用

`src/core/dice.parser.js` → `parseSettle()`：

```js
const myLines = raw.split('\n').filter((line) => line.includes(`【${userId}】`));
// 逐行累加 赢 金额 / 减 输 金额
```

问题有三层：

1. **语义未定**：代码假设「同一结算名单里本账号所有行的 赢/输 金额可以直接代数求和 = 账号净盈利」。这要求名单里每行金额已经是「该行净盈亏」，而不是「返还额」。生产库 `message_logs.raw_text` 被 `summarizeForLog()` 裁剪成 `第xxx期 骰子:N`，完整名单没落库；`app.log` 里 `期输赢` / `骰子为` 出现次数均为 0，日志也没留原文，**现有数据无法还原这条真实口径**，需要一条真实定位胆结算原文才能最终拍板。
2. **多规则重复套用**：`refineWinProfit()`（`action-log.dao.js` 271–281 行）按 `(bot_user_id, chat_id, round_period)` 把同期**所有**赢单动作的 profit 统一覆盖成这一份聚合利润。若同一账号同群同期存在多条定位胆规则，会把总额套到每一条上。当前生产只有一条启用规则（`id=4`），尚未触发，但属设计缺陷。
3. **盈利被名单覆盖后不回滚**：赢单先按 `_profitFor()` 记 `+4A`，再被名单修正值覆盖。名单修正值本身若是「含本金返还」而非净利，就会二次错账。

**建议**：把结算名单按行结构化落库（脱敏），保留 `行类型 / 号码 / 金额 / 是否命中`，按规则归属精确回填，而不是聚合覆盖。

### P1-3　模拟钱包与真实余额两条链路的金额口径已经分裂

- 下注时：`deductSimBalance(botUserId, c.stake)`，`c.stake` 是总投入 5A —— 正确。
- 结算时：`creditSimBalance(bet_amount + profit)`。因为 profit 被放大 5 倍，赢单实际入账 `5A + 4A = 9A`，而按 5.8 口径应该是 `5.8A`。**模拟钱包的资金曲线不只是偏高，而是数学上不成立**：赢 9A 输 5A，连输三次就超过赢一次。
- 止盈判定基于同一个 `sumProfit()`，所以止盈目标会被提前触发约 5 倍的速度。

### P2-1　`DICE_SPEC_PAYOUT` 是全局常量，不随群变化

`src/core/rule.engine.js` → `locationPayoutOdds()` 读 `process.env.DICE_SPEC_PAYOUT`，默认 5.8。生产 `.env` 未设置，走默认。

而 `chat_odds` 只学「大/小」赔率（`parseOddsSamples()` 只匹配 `【\d+】 大|小 金额,赢 金额`），**完全不学定位胆赔率**。生产 9 个群的大/小赔率实测为 0.95 / 0.9975 / 1 / 0.999 等，说明不同群、不同时间的赔率本身就不同；用同一个 5.8 覆盖所有群，一旦某群定位胆倍率不是 5.8，就会系统性偏差。

**建议**：把定位胆倍率做成群级参数（`chat_odds` 加 `spec_odds` 列，或新建群配置表），并从真实定位胆结算样本动态校准。

### P2-2　下注记录面板的金额展示会误导用户

`src/bot/panels/report.panel.js` 第 71 行：

```js
text += `${time}　${escapeHtml(chat)}｜${escapeHtml(dir)} ${escapeHtml(String(b.bet_amount))}　${result}\n`;
```

`bet_amount` 是整组总投入（50），方向标签是 `定位胆1/2/3/4/5`，用户看到「定位胆1/2/3/4/5 50」会以为是每个号码下注 50，实际是每注 10、合计 50。

**建议**：显示成「每注 10 × 5 ＝ 总 50」，或在库中拆出 `stake_per_number`。

### P2-3　mode=1 规则无法配置止损，`calcCumulativeStake` 的 mode 分支不可达

`rule.handler.js` 第 312 行：mode=1 时强制 `stop_loss: null`、`min_interval: 0`、`streak_count: 1`。而 `calcCumulativeStake(base, ratio, losses, mode)` 里专门写了 `mode === 1 ? NUMBERS_PER_BET : 1` 的 5 倍累计投入分支——但 mode=1 的规则永远没有 `stop_loss`，这条分支在当前向导下走不到。

这既可能是产品有意简化，也可能是功能缺口。按现状报告，不替主人定性。

### P2-4　过期注释与 schema 描述仍在误导维护者

- `migrations/010_spec_mode.sql` 写的是「大小照常下注 + 伴随一手定位胆」，`schema.sql` 的 `rules.mode` 注释写的是「1=SPEC_FIVE 大小+伴随5数定位胆」。
- 但**可执行代码里 mode=1 只下定位胆，不下大小**（`_tryArm()` 里 mode=1 分支直接 `pickNumbers()`，没有 `evaluateStreak()`；`describeRule()` 也写成「独立规则」）。

注释与实现相反，是这次审计中反复误导的来源之一，建议清理。

### P3-1　结算原文不可追溯，纠纷无法对账

- `message-dispatcher.service.js` → `summarizeForLog()` 把群聊原文压成一行摘要（dice → `骰子:3`，settle → `第xxx期 骰子:N`），名单全文不落库。
- 生产 `.env`：`MESSAGE_RETENTION_HOURS=1`、`ACTION_RETENTION_HOURS=1`，流水和动作记录每小时清一次。

结果：真实赔付口径无法事后核对，历史金额口径（单注 vs 总投入）也随记录一起消失。

**建议**：定位胆作为核心业务，保存结构化但脱敏的结算行（号码、金额、类型），而不是完整原文；保留期与业务重要性对齐。

### P3-2　`pickNumbers()` 的取数依赖 `message_logs` 写入时序

`_tryArm()` 用 `messageLogDao.recentValues(chatId, 40).slice(1)` 取号。当前骰子消息在分发器里先入库再调 `handleOpen`，所以 `.slice(1)` 确实排除了本期点数——这一点已核实无误，`pickNumbers()` 取到的是「本期之外最近出现的 5 个不同数」。

但该逻辑依赖「入库先于取号」这一隐式顺序，无显式契约。若将来调整分发顺序，取号会包含本期开奖号而不自知。
